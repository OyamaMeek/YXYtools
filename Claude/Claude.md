# 易校园校园卡余额变动 Telegram 推送：阶段规划

更新时间：2026-10-04，Asia/Shanghai。

## 1. 已确认需求与当前状态

- 目标：检测易校园校园卡余额变化，并发送 Telegram 通知。
- 运行平台：GitHub Actions，每半小时执行一次单次查询流程。
- 执行时间：北京时间每日 07:30 恢复，23:00 停止；最后一个计划执行时间为 22:30。
- 用户将把已砸壳的 IPA 放到项目根目录；收到文件名后开始分析。
- 当前仅进行规划，尚未授权开始产品实现。
- 当前根目录只有项目指导文件等文件，没有 IPA、产品代码、测试配置或 Git 仓库。
- 本文件是阶段规划。接口、状态保存方式和部分业务规则尚未明确，暂不生成最终 `AGENTS.md`，不修改现有 `AGENTS.md`。

## 2. 建议首期范围

以下是待用户确认的建议，不作为已确定需求：

- 一个个人账户、一张指定校园卡、一个 Telegram 接收聊天。
- 每次 Actions 任务查询一次余额，发现变化后通知；消息包含上次余额、本次余额、差额和检测时间。
- 第一次成功查询只建立基准；余额不变时不发送通知。
- 跨 Actions 执行保存查询基准和待发送消息，下一次任务继续处理。
- 支持查询失败、登录失效、推送失败的明确记录和恢复。

本规划不安排管理页面、多用户服务、统计报表、自动充值或支付功能；新增需求时另行确认范围。

## 3. 数据与通知边界

- 若接口只返回余额，只能检测两次成功查询之间的净变化。例如先扣款再充值到原余额，轮询可能无法发现期间发生的交易。
- 差额表示余额增加或减少。没有交易流水证据时，不把它断言为某笔消费或充值，不编造商户、交易时间或交易笔数。
- 检测时间与交易发生时间分别标记；首次查询及恢复查询不得伪造交易时间。
- 查询失败、字段缺失、金额无法解析、响应不属于指定账户或卡片时，不更新有效基准，不把错误转换为零余额。
- Telegram 返回明确成功后记录发送结果。结果不明确时保留待处理消息；选择重试后可能重复，无法承诺每条消息恰好送达一次。
- 服务离线期间若只有余额接口，恢复后只比较上次有效余额与最新余额，通知应说明检测间隔。
- 夜间不查询、不推送；次日 07:30 的任务恢复上次状态，比较最新余额，可能包含夜间净变化。
- Actions 定时任务可能延迟或被丢弃，半小时是计划间隔，不能承诺准点或半小时以内送达。

## 4. 分阶段任务与完成标准

### 阶段一：分析 IPA，确定查询可行性

- [ ] 确认文件名、文件完整性、应用版本、主程序与相关框架的加密状态；不修改原始 IPA。
- [ ] 在项目专用目录中保存分析产物；检查压缩包成员路径并使用成熟工具读取 IPA 和 Mach-O，不自行编写格式解析器。
- [ ] 查找余额页与登录流程相关的域名、路径、类、调用关系及可读资源；区分静态线索和验证结论。
- [ ] 确认目标学校、账户与卡片对应关系，整理必要参数、凭证来源、签名逻辑和余额单位。
- [ ] 确认 Token 有效期、刷新方式及验证码或设备校验依赖；缺少证据的项目明确记为未验证。
- [ ] 如静态信息不足，列出准确缺口及所需运行条件，再安排经授权的动态分析。

完成标准：交付脱敏的分析记录，说明能否独立查询、依据和阻碍。仅发现接口字符串不能判定查询已实现。是否需要运行 App 或动态分析，取决于样本结果。

### 阶段二：验证一次真实余额查询

依赖：阶段一获得足够的接口与鉴权信息，以及用户自己的有效登录条件。

- [ ] 使用实际账户进行只读查询，验证真实请求和结构化响应。
- [ ] 核对学校、账户、卡片、余额字段和金额单位；与用户同期提供的 App 余额证据比较。
- [ ] 将余额规范化为整数分或 Decimal，拒绝非有限数值和不符合真实协议的精度；不使用二进制浮点直接比较金额。
- [ ] 验证鉴权失败、超时和字段异常不会产生有效余额记录。
- [ ] 确认实际支持的会话续期方式；需要人工重新登录时给出明确恢复步骤。

完成标准：能从实际接口稳定取得指定卡片余额，鉴权限制与未完成验证逐项记录。若只能依赖手机环境查询，应重新评估运行方案，暂停依赖独立查询的实现。

### 阶段三：实现变化检测与 Telegram 通知

依赖：真实余额查询已通过；用户确认监测范围、通知规则和接收位置。

- [ ] 先为变化判定和状态恢复编写能够暴露目标问题的检查，再实现最小逻辑。
- [ ] 读取上次有效观察值和待发送消息；在同一次原子状态更新中保存新观察值及对应消息，避免推进基准后丢失通知。
- [ ] 确认状态已经保存到跨执行可读取的位置后再发送，不能把临时运行器文件视为持久保存。
- [ ] 使用 Telegram Bot API `sendMessage` 发送文本，检查 `ok` 与结果字段，不能仅凭 HTTP 成功判定已发送。
- [ ] 成功后持久保存返回的消息标识；失败时保留原消息，按顺序处理，已确认发送且已保存结果的消息不重复排队。
- [ ] 按实际错误分类：临时网络错误退避重试，限流遵守服务端等待时间，无效 Token 或接收权限错误停止重复发送并记录处理方法。
- [ ] 对登录失效或连续查询故障的告警按事件状态去重；如 Telegram 本身不可用，通过本地日志报告。
- [ ] 在用户授权的测试聊天验证真实送达，再结合用户正常使用产生的余额变化验证端到端流程；不主动发起充值或消费。

完成标准：有效余额变化生成正确消息，查询失败不误报，发送失败不丢弃消息，后续 Actions 执行可恢复。发送结果不明确、发送成功后进程终止或状态保存失败的重复风险必须说明。

### 阶段四：配置 Actions 定时执行并交付

依赖：真实余额查询和推送已通过，目标 GitHub 仓库及状态保存方式已确认。

- [ ] 在 GitHub 托管运行器验证易校园接口、登录流程与 Telegram 的网络可达性。
- [ ] 配置北京时间 07:30、08:00、08:30 至 22:30 的定时触发，工作流保存在默认分支。
- [ ] 脚本启动及每次发起余额查询、通知或重试前检查当前北京时间；允许窗口为 `[07:30, 23:00)`，窗口外不发起这些请求。
- [ ] 每次脚本执行完退出；配置有界超时、错误重试上限，以及所有监测入口共用的 concurrency 组，避免重复实例竞争状态。不取消正在发送和保存状态的任务。
- [ ] 恢复跨执行状态；首次初始化与已有状态读取失败分别处理，后者必须明确失败，不能清空记录后当成首次运行。
- [ ] 将登录配置、Bot Token 与 Chat ID 放入 Actions Secrets；如果登录会刷新凭证，依据已验证协议单独确定跨次保存方法，不能假设普通 GITHUB_TOKEN 可更新 Secrets。
- [ ] 将 IPA、提取目录、真实响应、私有配置及运行日志纳入项目忽略规则；状态仅通过已确认的保存位置持久化。
- [ ] 验证下一次执行恢复、延迟至夜间的任务、网络恢复及登录失效后的真实操作路径。
- [ ] 交付 Secrets 设置、手动运行、停用定时任务、日志查看、状态恢复及重新登录说明，以及实际可执行的验证命令。

完成标准：GitHub Actions 上完成一次真实查询到 Telegram 接收的流程，下一次执行正确恢复状态，时间边界检查通过。持续运行观察时长另行确认；当前尚未创建或启用工作流。

## 5. 推荐实现方式与文件职责

建议使用 Python 单次执行脚本完成查询、检测和发送，使用标准库 Decimal 或整数分处理金额。运行时版本及 HTTP 依赖在接口分析后锁定。

GitHub 托管运行器每次运行使用新环境，跨次状态必须显式恢复和保存。建议私有仓库通过独立 `state` 分支保存少量 JSON 状态，包含有效余额、检测时间、待发送消息和已确认的发送结果；凭证不得写入该状态。仓库可见性、状态分支及写入权限尚需确认，本次不创建分支或修改权限。

不将 Actions cache 作为唯一状态来源。实现时必须验证状态恢复、写入失败和并发保护；发送前保存待发送消息，发送成功后保存结果，两个阶段之间的终止可能导致下一次重复发送。

对应已确认时段的定时触发草案如下，仅供规划，尚未写入实际工作流：

```yaml
on:
  schedule:
    - cron: '30 7 * * *'
      timezone: 'Asia/Shanghai'
    - cron: '0,30 8-22 * * *'
      timezone: 'Asia/Shanghai'
```

这两条规则每天共计划执行 31 次。夜间限制检查使用实际运行时间，适用于定时及手动入口；窗口外不发起查询和推送。GitHub 的排队可能导致工作流在夜间启动，脚本此时直接跳过业务操作。

建议文件职责如下，实施前按实际复杂度调整；本次不创建产品文件：

| 文件 | 职责 |
| --- | --- |
| `client.py` | 已验证的鉴权、余额请求、响应校验 |
| `monitor.py` | 单次查询流程、时段检查、金额变化判定、状态更新、Telegram 发送与恢复 |
| `tests/test_monitor.py` | 实际状态读写、变化判定及时间边界检查 |
| `.github/workflows/monitor.yml` | 定时与手动入口、Python 环境、Secrets 注入、并发保护和状态保存 |
| `README.md` | 配置与实际运行说明 |
| `.gitignore` | 排除 IPA、分析产物、私有配置及运行数据 |

涉及签名或会话管理时，优先使用已安装且适合实际协议的库；不为单纯发送文本预先引入完整 Bot 框架。没有可靠鉴权证据前不写接口调用代码。
